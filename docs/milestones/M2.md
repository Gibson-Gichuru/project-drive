# M2 — Trip domain

Status: implementation under verification, started 2026-11-13 at the owner's explicit request. M1's real-world route-following/coverage gate remains open; starting M2 does not close it.

## Scope and rules

The Go API now owns private trips, active membership and lifecycle transactions in PostgreSQL/PostGIS. No paid identity service, Google location service or additional hosted component is required. Android trip screens remain M4; live sharing and immediate socket revocation remain M3. This milestone never turns on location sharing.

- Verified identities supply user UUID and display name. Clients cannot select an owner in a request body. Unknown identities are provisioned only during a successful authenticated operation; deleted identities cannot be resurrected.
- Owners create a planned trip and remain its owner/member. Owners can start planned trips, complete active trips, or cancel planned/active trips. Completed/cancelled states are terminal. Repeating the same transition succeeds; a different invalid transition returns 409. Completed/cancelled members retain read access.
- Active members can read the trip and its active member list. Non-members and former members get 404, hiding existence. Members can leave; the owner must end/cancel instead. Repeated leave is safe. Rejoining requires a usable invitation, consumes a new use, resets sharing to false and renews the join timestamp.
- Only owners create/revoke invitations. Each contains 256 random bits, has a 60-second to 24-hour lifetime and 1–100 uses. Only SHA-256 token hashes are persisted. Revocation and terminal transitions invalidate invitations. A duplicate join by an existing active member consumes no use, including a retry after the last use; expired/revoked invitations still fail. Invalid invitations return a generic error. A trip is limited to 100 active members including its owner; member reads return this bounded list without pagination.
- Each existing-trip transaction locks the trip row before invitation/membership changes. Concurrent redemption cannot exceed use/member limits or race a terminal transition/revocation. Transactions bound API work to five seconds. Future M3 delivery must reauthorize against membership, sharing and trip status; there is no live position state in M2.
- JSON requests are limited to 4096 bytes, reject unknown/irrelevant fields, and require lowercase UUID identifiers. Error responses contain code, message and request_id. Trip responses use no-store. Ordinary logs redact trip paths and never include bearer tokens, bodies or invitation secrets.

## Identity boundary

Development credentials use Ed25519-signed JWTs through vendored `github.com/golang-jwt/jwt/v5` v5.3.1 (MIT). Verification pins EdDSA, issuer `project-drive-local`, audience `project-drive-api`, UUID subject, display name, issued-at and expiry, with a maximum 15-minute lifetime. See [the library's validation options](https://golang-jwt.github.io/jwt/usage/parse/).

There is no HTTP token issuer. An offline developer command generates a private seed file (0600, exclusive create) and mints tokens. The API receives **only a public key**. Both configuration and identity-key construction require an explicit `APP_ENV=local` or `test`; auth configuration fails closed for unset, homelab and production environments. Never change homelab's environment to bypass this gate. Homelab can run migrations and navigation but all trip operations return 401 until a reviewed production identity implementation is added. The development command is excluded from the runtime image.

Private keys and tokens must remain outside git and screenshots/logs. The development issuer is intentionally not production authentication: there is no account enrollment, refresh, per-token revocation or untrusted-user access. Use only on a trusted workstation with loopback-only Compose ports. Production authentication remains a Phase 1 requirement; multi-phone Phase 0 tests will need a separately isolated local/test session, never development auth on the homelab.

## Safe retries

`POST /v1/trips` requires an `Idempotency-Key` UUID scoped to its owner. Retrying with the same key/name returns the same trip; changing the name returns 409. The key is retained for the lifetime of that trip.

`POST /v1/trips/{trip}/invites` also requires a key, unique within the trip. It creates at most one invitation per key. Because raw secrets are never stored, a repeated key returns `409 invite_already_created` rather than replaying the token. The error includes the original invitation ID so the owner can revoke it if the first response was lost, then use a new key. Owner-only lookup/revocation remains possible after expiry. No secret is retained for response replay.

## Reproduce locally

From the repository root:

```sh
make setup
# Use a path outside the repository; the command refuses to overwrite a key.
APP_ENV=local go -C services/api run ./cmd/dev-token -generate-key "$HOME/.local/state/project-drive-dev.seed"
```

Create the parent directory privately if it does not exist. Put only the printed public key in your ignored `.env` as `DEV_AUTH_PUBLIC_KEY=...`, keeping `APP_ENV=local`, then run `make up`. Mint two short-lived tokens with different UUIDs:

```sh
APP_ENV=local go -C services/api run ./cmd/dev-token -key "$HOME/.local/state/project-drive-dev.seed" -user 11111111-1111-4111-8111-111111111111 -name Owner
APP_ENV=local go -C services/api run ./cmd/dev-token -key "$HOME/.local/state/project-drive-dev.seed" -user 22222222-2222-4222-8222-222222222222 -name Member
```

Keep bearer strings private. Use `Authorization: Bearer …` and the [OpenAPI contract](../../contracts/openapi.yaml): create a trip with `{"name":"Demo"}`, create an invite with `{"expires_in_s":600,"max_uses":1}`, then redeem it as the other user with `POST /v1/trips/join` and `{"token":"…"}`. Trip creation and invitation creation require distinct client-generated `Idempotency-Key` UUIDs. No-body lifecycle endpoints reject bodies. A third authenticated user must receive 404 on the trip and member list. Refresh expired developer credentials offline.

`make integration` applies migrations twice, verifies the ledger, runs real PostGIS HTTP acceptance tests in an isolated temporary schema, and removes that schema afterward. It does not truncate existing application tables. `make ci` adds Go race/vet/security checks, Android assembly/unit/lint checks and deployment rendering.

## Migration and recovery

Migration `0002_trip_domain` is additive: nullable request keys, unique retry/owner indexes, and constraints for invite hashes and inactive sharing. It preserves existing rows and is applied transactionally under the existing migration advisory lock. The migration is forward-only. Rolling back the API image does not remove the added schema; the preceding M1 API ignores these additions. Preserve the database backup before deployment; do not drop schema or restore over newer data as an ordinary image rollback.

## Verification and release
