# M3 — Real-time hub

Status: **complete, 2026-11-13**. The owner explicitly deferred M1's real GPS journey and authorized M3; that field gate stays open in the roadmap and device record. Android convoy UI/two-phone sharing is M4, not claimed here.

## Behavior and authorization

The Go API now provides `GET /v1/trips/{trip}/stream`. It requires a verified bearer in the HTTP Authorization header, an active trip, active membership and explicit sharing. Native clients can omit Origin; browser Origins must match the request host. Query parameters/URL credentials are rejected. No network token issuer, external realtime service, Redis or metered dependency is added. `github.com/coder/websocket` v1.8.15 is vendored with its MIT license; see [the maintained library](https://github.com/coder/websocket) and [API documentation](https://pkg.go.dev/github.com/coder/websocket@v1.8.15).

`PUT /v1/trips/{trip}/sharing` with `{"enabled":true/false}` changes only the authenticated member's sharing consent. Enabling requires an active trip. Disabling clears their ephemeral position and closes their streams. It does not start Android GPS. The owner can `DELETE /v1/trips/{trip}/members/{member}` on planned/active trips, but cannot remove self. Removed members are banned from rejoining that same trip in Phase 0; ordinary leave permits an explicit invite-based rejoin, with sharing off. Migration `0003_member_removal` stores that distinction and constrains removed membership to be inactive.

All trip REST operations run through `tracking.Coordinator` and a context-aware single-instance gate shared with final socket writes. The domain transaction commits before reconciliation purges positions, invalidates subscriptions and queued deliveries. Every publish rechecks database authorization; sweeps recheck active trips at most one second apart. An authorization-store failure closes affected streams and purges their live state. Every queued position also checks its sender's current authorization generation at delivery: share-off/on, removal or leave cannot resurrect an old queued coordinate. Snapshots are built when delivered rather than freezing a pre-revocation view. Generation maps retain only currently authorized users, with a bounded monotonic counter across membership turnover.

The guarantee is no new server position write after a committed revocation, not retraction of bytes already written to a network before that commit. In-flight writes have a one-second budget by default. All future trip mutation entry points must use the coordinator. Direct database administration is not an alternative application API; its changes are checked on publish/subscribe/sweep. Multi-instance deployment would need distributed ordering/invalidation before it is safe.

## Live state and protocol

`PositionStore` and `Broadcaster` interfaces isolate the in-memory implementation. Coordinates are never inserted into Postgres or ordinary logs. Only bounded ephemeral latest positions, ordering watermarks, connections and outgoing queues are kept. Expiry clears the coordinate reference while retaining an ordering watermark as long as the bounded live trip remains; empty trips are evicted. Restart generates a new server-instance UUID and begins with no positions. Persisted sharing consent alone does not resurrect coordinates or start collection.

The first message is an authorized `trip.snapshot`; then `participant.position`, `participant.joined` and `participant.left` events use server-assigned trip sequence numbers and an instance UUID. A new snapshot resets the client's baseline; an idle trip eviction may reset its sequence, so reconnect must always resync. A participant joins/leaves the **live sharing set**, not just the general member roster. Terminal `trip.ended`/`error` controls are best effort before closure; closure/reconnect authorization remains authoritative.

Client text messages contain only type=`position.update`, version=1 and a payload with latitude, longitude, positive accuracy and RFC3339 recorded time; optional speed/heading are bounded. Unknown routing/identity fields, malformed/binary/oversized messages and invalid numbers close the offending stream. Identity comes from the verified session. Older or equal recorded timestamps are silently dropped across reconnects while the live trip exists. Incoming time is limited to 15 seconds old / 5 seconds ahead by default; future skew cannot extend freshness because effective time is the earlier of recorded/received time.

Snapshots mark stale positions at ten seconds by default and exclude expired positions. Clients must continue aging markers using timestamps and supplied stale/TTL metadata; no periodic stale-position heartbeat is implied. At 30 seconds by default, expiry removes the position and broadcasts participant.left. Read snapshots with a 64 KiB client limit; client updates default to at most 4096 bytes. Outgoing snapshots/frames are also capped at 64 KiB.

See [the full event schema](../../contracts/websocket/events.json) and [REST/upgrade contract](../../contracts/openapi.yaml). No long-lived tokens belong in URLs. JWT sessions are closed on expiry (also checked on publish and write); reconnect with a fresh offline-issued local/test token and reauthorize.

## Bounds and lifecycle

Defaults in `.env.example`: 64 connections, two per user per trip, 16 live trips, 1,024 position/watermark entries, 16 queued events per connection, two updates/second with burst five. A full send queue drops that slow consumer; size/rate/capacity errors never allocate unbounded buffers. Each trip is already capped at 100 active members. Server ping runs every 15 seconds with a five-second pong budget; an active read loop must process control frames. Write budget is one second; authorization work has bounded request/sweep contexts. All limits validate startup and can be configured through TRACK_* environment variables, with hard maximums.

The homelab API Deployment uses `Recreate` with one replica. Upgrades deliberately disconnect streams and clear ephemeral positions; clients reconnect and resync. This avoids overlapping independent hubs during rolling updates and introduces brief prototype downtime. Code rollback does not restore live coordinates. M3 is not a measured throughput, latency or battery guarantee; those are M6 gates.

## Reproduce and recovery

`make integration` migrates twice and runs real PostGIS HTTP and WebSocket acceptance tests in disposable schemas. It creates ephemeral Ed25519 identities in memory and two actual WebSocket clients, without storing credentials or private GPS. `make ci` adds Go vet/race/security, Compose/Kustomize and Android build/test/lint checks. Unit tests cover the store, parser, limits and the race between an in-flight coordinate write and a committed revocation.

For manual local use, follow [M2 offline identity setup](M2.md), create/join/start a trip, enable sharing for both users, then connect with Authorization headers and the optional `project-drive.v1` subprotocol. Read the snapshot before publishing; run a reader continuously so Ping/Pong works. Send only fixed synthetic positions for developer tests. Reconnect must obtain a fresh snapshot and must not restore client-cached positions as current.

Development identity remains hard-disabled outside explicit local/test environments. The homelab ships the code/migration but trip, sharing and stream access remain 401 until reviewed production authentication exists. A local/test session with authorized device forwarding remains the Phase 0 test path; do not relabel homelab as local to bypass the guard.

Archive inventory was verified; no full restore rehearsal is claimed. Homelab preflight found no users/trips and migrations 0001/0002 present.
