# Project Drive delivery roadmap

This roadmap turns `SPEC.md` into a sequence of reviewable releases. The spec remains authoritative; this document organizes its requirements into milestones, outcomes, dependencies, and go/no-go gates. Dates in the spec are effort estimates for focused solo development, not delivery commitments. No calendar dates are assigned until the first milestone is sized against the actual team and environment.

## Open-source and zero-service-fee constraint

Use open-source software and open data, with no required proprietary mapping, authentication, location, or telemetry SDK; paid API; usage-billed service; or paid hosted dependency. The normal development and self-hosted deployment path must work without third-party service charges. Keep provider interfaces replaceable and document all licenses, attribution, data obligations, and resource requirements. This is a **zero paid service-fee** target, not a claim that running servers, storage, internet access, devices, or domain names has no real-world cost. The project can avoid hosting charges by running on developer/team-owned hardware; availability and public reach then depend on that hardware and connection.

For mapping, use OpenStreetMap data with an open Android renderer such as MapLibre and self-hosted OSM-derived tiles and routing. Evaluate Valhalla as the first routing candidate. Do not use the public OSM tile or Nominatim endpoints as an assumed production backend: the OSM Foundation distinguishes free data from limited, best-effort public services and imposes usage policies. Any temporary public endpoint use must be policy-compliant, replaceable, and explicitly marked as a development dependency.

Official starting references: [MapLibre Native](https://maplibre.org/projects/native/), [Valhalla](https://valhalla.github.io/valhalla/), [OSM Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/), and [Nominatim Usage Policy](https://operations.osmfoundation.org/policies/nominatim/). Recheck these at M1; the public service policies can change.

## Product outcome

Deliver an Android driving companion in deliberate increments: first a runnable developer prototype, then a useful navigation and road-intelligence experience, then reliable private convoys, then personal telemetry and heatmaps, and finally a security-reviewed private beta.

The first end-to-end working release is the **Phase 0 private alpha**: a physical-device route demonstration, authenticated private trip creation and joining, opt-in live sharing between two phones, and a basic post-trip telemetry summary. It is for controlled development use; it is not production-ready authentication or a public release.

## Cross-cutting completion rules

- A milestone is done only when its code, tests, documentation, and acceptance gate are complete. Keep the build runnable at every step.
- Enforce authenticated active trip membership on every REST and WebSocket read/write. Derive user identity from verified credentials; never trust a client-supplied owner ID.
- Location sharing is explicit and revocable. Redact coordinates from ordinary logs, bound live state and local buffers, label stale positions, and define retention before production.
- Keep navigation types behind `NavigationEngine`. Do not add vendor keys or credentials to git. Record provider and policy evidence in the decision record.
- Keep Phase 0 live location state single-instance and ephemeral. Add Redis/pub/sub only when multi-instance deployment is in scope.
- Prefer self-hosted and open-source services with no metered external APIs. Open-source licensing does not make hosting, hardware, data transfer, or support free; record software licenses and real operating requirements.
- Attribute OSM data and comply with ODbL and source-specific terms. Do not bulk-fetch or depend on public OSM tile/geocoding demo servers for production traffic.
- Keep geocoding/address search separable from routing. Phase 0 may use a typed destination or map pin until a compliant self-hosted search service is ready.
- Use measurable acceptance evidence. Do not mark physical-device, licensing, pricing, legal, latency, battery, or security checks as passed without doing them.

## Decisions and risks to resolve at the relevant gate

1. **OSM stack and local operations:** M1 must validate OSM road coverage and routing quality in the actual Kenyan target area, choose self-hosted map tile and routing components, assess device/server hardware needs, and record ODbL attribution/share-alike obligations. MapLibre is a candidate renderer and Valhalla a candidate router; neither decision is final until the physical-device spike passes.
2. **Identity:** M2 needs a local/test-only identity mechanism with a hard guard against use in other environments; select a self-hostable open-source production identity solution before Phase 1 release; do not add a paid hosted identity dependency.
3. **Location permissions and background behavior:** M4 must use foreground-first collection and verify current Android and Play policy requirements before requesting anything broader.
4. **Privacy and retention:** Before Phase 3 or beta, agree what history is retained, for how long, how users export/delete it, and how backups are purged.
5. **Compliance and operational readiness:** Before invited beta, review Kenyan data-protection obligations and applicable platform/provider rules, and define support, incident response, backup, and restore procedures.
6. **Performance targets:** Measure the stated receipt-to-broadcast latency and battery behavior in representative field conditions; adopt thresholds from observed results and product needs.
7. **Cost boundary:** Decide what hardware and network access the team already has, and whether Android app distribution will be self-hosted or use an open distribution channel. The application can avoid paid service dependencies, but a publicly reachable hosted service cannot be promised to have zero operating cost solely because the software is open source.

## Working cadence

The owner explicitly requested starting M2 on 2026-11-13 before the M1 field gate closed. Implement and verify M2 while preserving that open gate. Complete the remaining M1 physical route/coverage validation before declaring Phase 0 complete. At each milestone review, compare evidence with its gate, record changed scope and decisions, and either close it or list the concrete blocker. Do not begin later milestones until the current gate passes. Revisit phase scope after M6 field results, and re-estimate work before making delivery-date commitments.
